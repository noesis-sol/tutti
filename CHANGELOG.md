# Changelog

## Unreleased

- The project scaffold: Bun, Effect and OpenTUI, with `scripts/check.sh` (tsc, Biome, the tests and shellcheck) and `bun src/main.ts` printing the version.
- `test/test-script.test.ts` runs `scripts/test.sh` on flaky and broken fixtures; `docs/spikes/08-bun-test-retry.md` reports why the script reruns failed tests by name rather than reading `--retry`.
- `src/services/exec.ts` runs every external command in a process group of its own, with a time limit that kills the whole group (`CommandTimedOut`), interruption that does too, bounded output with an optional output file, and `CommandFailed { command, exitCode, stderr }`; `TimeLimit.read` (30 s) and `TimeLimit.write` (2 min) are orchestra's presets.
- `src/ui/sanitize.ts` makes untrusted text safe to show (§ 7.10): `sanitize` and `sanitizeLine` drop control characters, whole ESC sequences and bidi controls, and `escapeMarkdown` escapes text for Markdown; `test/sanitize.test.ts` proves it with fast-check.
- `src/project/settings.ts` and `src/project/userConfig.ts` define `.tutti/settings.json` (§ 8.4) and the user config at `$XDG_CONFIG_HOME/tutti/config.json` (§ 8.5) with Effect Schema: every key has a default (orchestra's where the spec is silent), times such as `"30m"` decode to Durations, and `readSettings` and `readUserConfig` return the value or `ConfigFileInvalid` with every problem (file, key path, message), an unknown key or a refused `permission_mode` (`bypassPermissions`, `plan`) among them.
- `src/services/Beads.ts` is every `bd` call a run makes (`ready`, `show`, `list`, `update` with `--claim`, `--status` and `--append-notes`, `close`, `defer`, `label add`/`remove`, `dep add`/`list`, `create`, `human list`, metadata get, set and unset), with orchestra's limits (30 s reads, 2 min updates) and `--json` decoded with Schema into `Issue`s; errors are `BeadsFailed`, `BeadsTimedOut` and `BeadsUnreadable`. `src/testing/Beads.ts` is an in-memory backlog with bd's ready, blocking, close-refusal, label and metadata semantics; `test/beads.test.ts` decodes recorded outputs in `test/fixtures/bd/`, fuzzes decoding with fast-check, and (slow) checks the in-memory backlog against a real bd.
- `src/services/Git.ts` is every git command a run makes (worktree add, remove, list and prune; branch create and delete; rebase and `rebase --abort`; merge-base; `merge --ff-only`; log `base..HEAD` with messages; `status --porcelain`; `diff --name-only base...HEAD`; `ls-files`; `rev-parse`, `--git-common-dir` included; the current branch), with orchestra's limits (30 s reads, 2 min writes) and `-z` output; errors are `GitFailed { op, stderr }`, `GitTimedOut` and `RebaseConflict { files }`. A rebase interrupted, timed out or refused is aborted, leaving the branch as it was; one stopped on conflicts stays stopped. `GitWriter` is a `Semaphore(1)` every write takes, re-entrant for the fiber holding it. `test/git.ts` makes real repositories with commits, branches and worktrees for git-subject tests; `test/git-service.test.ts` runs each operation against one (slow).
- `src/testing/Git.ts`, Git's test layer (§ 3.3, § 13): an in-memory repository with branches, worktrees (each with a HEAD, an index and a working tree), commits holding whole trees, rebase that replays a file at a time and stops on files both sides changed (left in progress, for `Repository.continueRebase` or `rebase --abort`), fast-forward that refuses a branch that isn't a descendant, status, diff names and ls-files; writes take the GitWriter it provides. Its `Repository` commits and writes as a worker would, detaches HEAD, deletes a worktree's folder, forces a conflict on a branch's next rebase, makes the next call of any operation fail or time out, and records every call, so scenarios reach `OFF_BRANCH`, `DIRTY_WORKTREE`, `REBASE_FAILED`, `MERGE_CONFLICT` and `MERGE_FAILED` without git. `test/git-memory.test.ts` runs one set of expectations against it and (slow) against real git.
- `spikes/opentui-soak/` soaks an OpenTUI React app (16 cards at 10 Hz over a transcript of 200, 600 or unbounded items) for 30 minutes and checks the renderer options and test-utils; `docs/spikes/05-opentui-soak.md` reports that the bounds hold OpenTUI's native memory but React's development build grows without bound under Bun.
- `src/cli/AppConfig.ts`, the AppConfig service (§ 3.3): the run flags of § 8.2 (`src/cli/flags.ts`, parsed with effect/cli), each with its `TUTTI_*` variable, resolved over the user config, the settings and the defaults into one value, the colour scheme's name in § 7.11's order; every problem with a flag, a variable or a config file comes back together in one `SetupProblem`. On-or-off values take 1, true, yes or on and 0, false, no or off; orchestra's unprefixed variables are not read. `src/testing/AppConfig.ts` gives a literal value.
- `src/native/libc.ts` binds libc through `bun:ffi` for darwin and Linux (§ 9.1, § 9.2): `openCloexec`, `flockExclusiveNonBlocking` and `unlock`, `createExclusive` (O_EXCL, mode 0600), and `openUnder`, which walks a path below a directory with `openat` and `O_NOFOLLOW` and refuses a symlink at any component (`SymlinkRefused`, naming it) or a path that isn't plain (`PathRefused`); other failures are `LibcError` with errno's name. Flags come from `node:fs` (they differ between Linux x86_64 and arm64), `O_CLOEXEC` from a table per OS, and darwin arm64's variadic mode is padded onto the stack.
- `src/services/Store.ts`, the Store service (§ 3.3, § 4.8): `.tutti/run/state.json` in the main checkout, defined with Effect Schema (its version, the run that wrote it, and per ticket the session ID, worktree, branch, why it was suspended, its phase on leaving, its resume count and the run's metadata). Every write goes through one fiber and is atomic (a temporary file in the same folder, fsynced, then renamed), and returns once on disk, so a session ID saved before its session starts survives a crash; an unreadable file is `StoreUnreadable` naming it, a failed write `StoreWriteFailed`. `src/testing/Store.ts` keeps the state in memory.
- `src/run/log.ts`, the Log service (§ 3.3): `.tutti/tutti.log` lines as orchestra writes them, `2026-10-17 09:05:03 <text>`, run-level lines at the margin and a ticket's indented two spaces, naming tickets by ID (§ 5). Text reaches the log only as a `Line`, from the `line` template or a builder, every argument through `sanitizeLine`; builders word the START block, HOLD, RESOLVING, FIXING, PERMISSION and QUESTION (with their `tutti answer` command), answers, ALLOWED, DENIED, STEERED, RELEASED, MESSAGE, USAGE, USAGE_LIMIT and PHASE_BUG. `sink: "stdout"` prints each line for plain mode (§ 7.6). `src/testing/Log.ts` captures lines; `test/log.test.ts` covers the format, sanitising (with fast-check) and the sink.
- `src/run/events.ts` defines every event stream record with Effect Schema (§ 10): `v` (1), `time`, `run` and `kind`, orchestra's twenty kinds with v0.7.7's fields, and tutti's `phase`, `attention`, `attention_answered`, `denied`, `usage_limit`, `message`, `steered`, `released`, `suspended` and `resumed`; `start` has `billing` and `permission_mode` and no `terminal`, `hold` has `lifted`, and `stop`'s word `AGENT_FAILED` replaces `TERMINAL_FAILED`. Untrusted text is kept as it came, JSON-encoded, with DEL, C1 controls, line separators and bidi controls escaped too. `src/run/eventstream.ts`, the EventStream service, appends each record to `.tutti/run/events.jsonl` as one line in a single write, opened with `openUnder` so a symlink in its path is refused, keeping every run; a stream that can't be opened or written warns once and the run goes on. `src/testing/EventStream.ts` captures records; `test/eventstream.test.ts` round-trips every kind, with examples and schema-derived samples.
- `src/services/Checks.ts`, the Checks service (§ 3.3): runs `checks.setup`, `checks.fast` and `checks.full` with `sh -c` in a given folder through exec, each within its own limit from AppConfig (the setup within the limit of the check it comes before), the whole output in the file the caller names (`check.log` or `setup.log`). In memory it keeps only what orchestra says of the output, bounded: the lines that say what failed (orchestra's patterns, each once, at most 30), the last lines, the `FLAKY:` lines and the `SUITE:` names. Results are `CheckPassed` (or `NoCheckCommand`), `CheckFailed`, `CheckTimedOut` and `CheckNotRun`; a time limit or interruption kills the check's process group. exec's `Command` gains `onOutput`, which sees each chunk as it comes. `src/testing/Checks.ts` plays scripted results and records the runs.
- `src/services/RunLock.ts`, the RunLock service (§ 9.2, § 11): `acquire` takes `flock(LOCK_EX|LOCK_NB)` on `<git-common-dir>/tutti.lock` and on orchestra's `orchestra.lock`, both opened close-on-exec, for the caller's scope, writing the run's JSON (pid, start time, version, branch, scope or feature, `"init": true`) to the first and orchestra's shape (`version` as `tutti <version>`) to the second. Another run holding either is refused with `AlreadyRunning { program, repo, holder }`: `tutti is already running in <repo> (pid 44497, since 08:31, main)` or `orchestra is running in <repo> (pid …)`. `src/testing/RunLock.ts` keeps the locks in memory; `test/run-lock.test.ts` refuses a second process and an orchestra, and shows both locks released on scope close, on `kill -9`, and despite a child the holder started.
- `src/services/Worktrees.ts`, the Worktrees service (§ 3.3, § 9.1, § 11): a ticket's worktree at `<worktrees>/<id>` on `tutti/<id>`, made from the base, or reused (its worktree, or its branch alone) with what the earlier attempt left reported (commits on `<base>..HEAD` and `git status`); `/.tutti/run/` added to the repository's `info/exclude` once, atomically, keeping the other lines; files under a worktree's `.tutti/run/` opened only through `openUnder`, a symbolic link in place of `.tutti`, `.tutti/run` or a run file refused with `RunFilesOutside`; removal of the worktree and then its branch. Ticket IDs that could escape a path or can't name a git branch, or hold control or invisible characters, are `BadTicketId` (orchestra's rules, proven with fast-check). `src/testing/Worktrees.ts` makes plain temp folders; `test/worktrees.test.ts` runs the live layer against real git (slow).
- `src/project/templates/worker-prompt.md` is tutti's built-in worker prompt (§ 4.11): orchestra v0.7.7's rules, with tutti as the orchestrator, branches `tutti/<id>`, a decision that can wait as a `human` question ticket and a quick choice as `AskUserQuestion`, checks in the foreground because a background wait holds the worker's place and its merge, and a message from the maintainer followed before carrying on; the time limit and the `--ticket` line are left to the first message. `src/project/prompt.ts` loads the prompt from `--prompt`, else `.tutti/worker-prompt.md`, else the built-in, drops the paragraphs naming `AskUserQuestion` when `workers.ask_user_question` is off, and replaces `TICKET_ID`; a missing or empty `--prompt` file, an empty project file and a prompt without `TICKET_ID` are setup problems.
- `src/agent/WorkerState.ts`, a worker's state (§ 4.2) as a tagged union (`Starting`, `Working{doing}`, `Retrying{attempt, max, status}`, `NeedsYou{requests}`, `UsageLimited{resetsAt}`, `Idle{at}`, `Closed`, `Gone{why}`) and `step`, a pure reducer folding SDK messages, hook callbacks, the count of open attention requests and the session's end into it. `Idle` needs the turn's clean result with nothing queued and no live background task but ambient ones; an `is_error` result on status 429 or a rejected `rate_limit_event` is `UsageLimited`, any other is a failed turn (not settled, its error kept); `api_retry` holds until the turn's next message; `doing` is classified as orchestra classifies tool calls. `settled` is true for `Idle`, `Closed` and `Gone` only. `test/worker-state.test.ts` has a table per rule and fast-check properties.
- `src/agent/Attention.ts`, the Attention service (§ 4.5): `request(ticket)` gives a session's `canUseTool` and `elicitation(ticket)` its `onElicitation`; each call becomes an `AttentionRequest` (tutti's ID, the ticket, `toolUseID`, `agentID`, `Permission`, `Question` or `Elicitation`, the sanitised display fields, `defaultToNo`, `suppressAlwaysAllowRule`, its creation time) queued per worker, oldest first, awaiting an answer. Answers give § 4.5's SDK results exactly; Allow for this run passes only the `addRules` suggestions, their destination rewritten to `session`, and keeps their rules so a later request from any worker suggesting only kept rules is allowed without asking (`ALLOWED … by a rule you allowed for this run`). An answer to a request no longer open fails `NotOpen`, one that doesn't fit it `DoesNotFit`; a request whose signal aborts is withdrawn. Requests and answers are PERMISSION and QUESTION log lines and `attention` and `attention_answered` events, tallied per ticket; `open` and `openFor(ticket)` stream the open requests, and `overdue` gives those open past the 4-minute `BLOCKED` limit. `src/testing/Attention.ts` adds a policy that answers as requests open (`allowAll`, `denyAll`); `test/attention.test.ts` covers each answer's result, queues, run rules, stale and withdrawn requests and elicitations.
- `src/agent/attentionFiles.ts` answers attention requests without a dashboard (§ 4.5, D20): each open request is `.tutti/run/attention/<request-id>.json` in the main checkout (the ticket, the kind, the sanitised display fields, the options, the two flags and the creation time), created exclusively with mode 0600 in a 0700 folder and removed once answered or withdrawn. The run watches the folder (`fs.watch` plus a 2-second poll) for `<request-id>.answer.json` and takes one only if it isn't a symbolic link, belongs to the run's user, answers a request still open, and fits its kind and options (allowing a `defaultToNo` request needs `confirm`); a taken answer resolves the request as one given on screen, logged and recorded `via` `answer_command`, and a refused one is an `ANSWER_REFUSED` line and `<request-id>.refused.json`. `tutti answer` (`src/answer/answer.ts`, registered in the new subcommand table `src/cli/commands.ts`, which `src/main.ts` now runs) lists the open requests (`--json` for scripts) or answers one with `allow`, `allow-run` or `deny`, `--reason`, `--choice` (once per question) and `--confirm`, checking the answer first, then waits up to 10 seconds for the run to take it and says whether it did. `test/attention-files.test.ts` covers the files, each refusal, parsing with fast-check, and the command against a running Attention service.
- `src/agent/Transcripts.ts`, the Transcripts service (§ 3.3, § 4.4): every SDK message of a worker's session but the partial `stream_event`s is appended to `.tutti/run/workers/<id>/messages.jsonl` in the main checkout as one line (`v`, tutti's sequence number, the session ID, the time and the SDK message), numbering on across resumes and runs, and its stderr to `stderr.log` beside it, both opened with `openUnder`; a torn last line is skipped, and the next item starts a line of its own. In memory each worker keeps its last 200 items, the latest action for its card (the current tool call as `Bash(scripts/check-fast.sh)`, else the last line of its text), and, only while a view is open, the live message partial messages fold into; `view` gives a scoped view its items and every update after them. `page` reads the transcript back 200 items at a time before a sequence number, and `tail` the last N items within M characters for triage. `src/testing/Transcripts.ts` keeps the files in memory; `test/transcripts.test.ts` covers both, with fast-check for the lines and the latest action.
- `src/agent/env.ts`'s `workerEnv` is a worker's environment (§ 4.1, § 4.13): tutti's own, with `CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1`, `CLAUDE_CODE_STARTUP_FAILURE_RESULTS=1`, `CLAUDE_CODE_FORK_SUBAGENT=0` and `CLAUDE_AGENT_SDK_CLIENT_APP=tutti/<version>`, and without `ANTHROPIC_API_KEY` beside a subscription login unless billing is `api`. `src/agent/Account.ts`, the Account service (§ 3.3, § 4.13), probes the login with one session that is sent nothing, run without the key: the account, how workers are billed and the `START` block's `billing:` line, the permission mode in effect and its `permission mode:` line; no login is `NotLoggedIn` and settings files Claude Code skipped (read from the session's `getSettings()`, as Claude Code 2.1.301 leaves them out of `initializationResult()`) are `SettingsUnreadable`, both at once when both. `src/testing/Account.ts` gives a literal account.
- `src/agent/mcp.ts`, MCP servers (§ 4.6): `resolveServers` resolves each name in `workers.mcp_servers` on this machine in Claude Code's order, local (the user's `.claude.json` under the repository's project entry, matched through symbolic links), project (`.mcp.json`), then user, with `.claude.json` in `CLAUDE_CONFIG_DIR` when set; `mcpServers` gives the definitions for the SDK's `mcpServers`, in memory only. A name defined nowhere, a claude.ai connector, a definition that isn't stdio, sse or http and a config file that can't be read are setup problems, all at once; no names gives no servers and a START note saying so (§ 15, Q5). `checkInit` checks a session's `system/init`: its `mcp_servers` must be exactly the chosen names, each with source `dynamic`, `sdk` or its scope (statuses aren't compared), else `workers got MCP servers they weren't given: <names>`. `test/mcp.test.ts` uses the config folders in `test/fixtures/mcp/`.
- `src/agent/options.ts`'s `workerOptions` builds a worker session's SDK options (§ 4.1) as a pure function: the worktree as `cwd`, the main checkout as `projectConfigRoot`, `settingSources` user, project and local, the permission mode always passed, the model and effort only when set, the `claude_code` preset with the standing rules appended and `snapshot: true`, `sessionId` for a new session or `resume` for a resumed one, the chosen MCP servers with `strictMcpConfig`, Attention's and Transcripts' callbacks, the hooks, subagent text and partial messages, `workerEnv()`'s environment, `--claude`'s executable when given, and `AskUserQuestion` disallowed when `workers.ask_user_question` is off. `spawnInOwnProcessGroup` starts Claude Code detached, leading a process group of its own, and passes its stderr to the transcript, which the SDK doesn't read from a custom spawn. `src/agent/hooks.ts`'s `activityHooks(ticket, recorder)` gives in-process `PreToolUse`, `PostToolUse`, `SubagentStart`, `SubagentStop` and `PreCompact` callbacks (§ 4.2) that return `{}` at once, record activity and compactions in a fiber of their own, and log and swallow any failure. `test/worker-options.test.ts` covers both.
- `src/agent/AgentHost.ts`, the AgentHost service (§ 3.3): `start` (with a session ID the caller draws), `resume` (with the message that carries it on), `send` (`client_composed`, or `origin: { kind: "human" }`), `interrupt` (its receipt), `close` (on purpose, the ID kept) and `end` (the worker forgotten, its streams ended); per worker a `WorkerState` stream from a `SubscriptionRef` and its sessions' raw messages; errors `AgentStartFailed { reason, startupFailureReason }`, `AgentGone` and `AgentProtocol`. `makeWorkers` is what both layers share: each message recorded in Transcripts, published and folded into the worker's state with its open attention requests. `src/testing/AgentHost.ts` plays scripted sessions per ticket (SDK messages, hooks, `canUseTool` and elicitations answered through Attention, waits for a message or an interrupt, sleeps on the Clock, effects, gone sessions, failed starts) and records everything it is sent; its helpers build the common scripts: claims and closes its ticket with a commit, defers, files a question, asks permission, hits the usage limit. `test/agent-host-scripted.test.ts` runs them under TestClock.
- `src/run/phase.ts`, the ticket state machine (§ 5.1): `TicketPhase`, a tagged union of the fourteen phases (`Queued`, `HeldBack{why}`, `Working{activity}`, `ToMerge{place}`, `Merging{step}`, `Resolving{attempt}`, `Fixing{attempt, afterResolution}`, `Done{outcome}` merged with its commit or with no change, `Asked{question}`, `Waiting{for}`, `Deferred{why}`, `Review{why}`, `Blocked{why}`, `Stopped{why}`) with `TicketPhaseSchema` for the event stream; typed causes; § 5.1's transition table as data (from, cause, to, what is recorded), with the carry-over of "The next run" as entries from outside; `transition(phase, cause)`, the only way to change a phase, giving the next phase or `InvalidTransition` (its `PHASE_BUG` line); `refine` for a phase's details (a Working ticket's activity, a place in the merge queue, a merge's step); and what the UI and totals read: `hasCard`, `countsUnder`, `isFinal` (only `Done`) and `stopsAtEnd`. `test/phase.test.ts` tests every row, rejects every pair the table doesn't list, and drives random causes with fast-check: no unlisted transition is taken, and `Done{merged}` is reached only from `Merging`.
